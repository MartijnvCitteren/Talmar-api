# Vacancy

The vacancy is the first aggregate and the start of every recruitment flow: a recruiter creates it in stages, and later
it gets published to job boards and receives candidates.

## Domain model

`Vacancy` (`domain/vacancy`) is the aggregate root, created through its builder:

| Field | Type | Notes |
|-------|------|-------|
| `id` | UUIDv7 | Generated by the builder unless given explicitly (used when loading from the database). |
| `jobTitle` | String | Required. |
| `language` | `Language` | Required. ISO 639-1 language of the vacancy texts: `NL`, `EN`, `DE`, `FR`, upper case in the contract too, like the country code. A value outside the enum (e.g. lower-case `nl`) is a `400`. AI generation writes the draft in this language. |
| `category` | `VacancyCategory` | Required. Fixed list of 21 job categories, incl. `OTHER`. |
| `location` | `Location(country, city)` | Required; both parts non-blank. The contract restricts `country` to ISO 3166-1 alpha-2. |
| `workplaceType` | `ONSITE` / `REMOTE` / `HYBRID` | Required. |
| `hoursPerWeek` | `HoursPerWeek(minHours, maxHours)` | Required. `BigDecimal`, so part-time hours like 32.5 are exact. |
| `status` | `VacancyStatus` | `DRAFT`, `PUBLISHED`, `FILLED`, `CLOSED`. Defaults to `DRAFT`. |
| `description` | `VacancyDescription` | Optional, see below. |
| `createdAt`, `lastModifiedAt`, `modifiedBy` | from `BaseObject` | `createdAt` is required and passed in by the use case. |

`VacancyDescription` is a value object with five optional texts (`summary`, `jobDescription`, `tasks`, `whatWeOffer`,
`aboutUs`) and a `source`: `MANUAL` (typed by the user) or `GENERATED` (reserved; not set by any use case). A draft
from AI generation (`generation.md`) is saved through the manual endpoint and therefore has source `MANUAL`: the user
reviewed and submitted it. It is replaced as a whole, never edited field by field.

The aggregate has no behaviour beyond construction and setters yet: no status transitions, no rule that
`minHours <= maxHours`. Add such rules to the aggregate when the use case that needs them is built.

## Implemented use cases

### Create a vacancy — `POST /vacancy`

`CreateVacancyService` builds a `DRAFT` vacancy from the core fields (job title, language, category, location,
workplace type, min/max hours per week), stamps `createdAt` from the `Clock`, and saves it. Returns `201` with the `VacancyResponse`.
The rest of the vacancy is added in later steps; this is the "staged creation" the contract describes.

### Set a manual description — `POST /vacancy/{id}/description`

1. `VacancyDescriptionContentValidator` rejects raw HTML/script-like tags and control characters (newline, carriage
   return and tab are allowed; rules in `TextContentRules`) → `400` naming the field. Length limits come from the contract (bean validation).
2. `SetManualVacancyDescriptionService` loads the vacancy (`404` if missing), replaces its description with a new
   `MANUAL` one and saves it.
3. Returns `201` with the `VacancyDescriptionResponse`.

AI generation is a separate endpoint (`generation.md`) whose drafts the user edits and then submits here. This
endpoint never generates text itself, which keeps the human in control of what gets saved.

## Contract-only operations

The contract also defines list, get, update (`PATCH`, which accepts `language`), delete (soft delete, status
`ARCHIVED`), publish, fill, close, plus contact person and offer/salary data on the vacancy. None of this is
implemented: the controller answers these with `501` problem details (`EndpointNotImplementedException`). The domain
has no `ARCHIVED` status, contact person or offer yet.

## Persistence

- Two tables: `VacancyJpaEntity` (with `language` as a `NOT NULL` column) and `VacancyDescriptionJpaEntity`, whose
  text columns have the contract's maximum lengths (1000 / 5000 / 5000 / 2500 / 2500). The description shares the
  vacancy's primary key (`@MapsId`), so a vacancy can have at most one description row. It is fetched eagerly, because
  the aggregate is always loaded whole.
- `VacancyRepositoryAdapter.save` writes vacancy and description in one cascaded save. When the description is
  removed, it deletes the row explicitly, because `orphanRemoval` does not fire when merging a freshly mapped entity
  graph.
- All vacancy fields are `@ProcessData`: a vacancy holds no personal data. `modifiedBy` (from `BaseJpaEntity`) is the
  only `@PersonalData` column, and it is not filled yet.

## Known gaps

- `listVacancies` is declared in the contract as `GET /vacancy/{id}/generate-description` (it sits under the wrong
  path and takes a vacancy `id`). Moving it to `GET /vacancy` is a breaking contract change; do it when the listing is
  built.
- `CreateVacancyService` has no `@Transactional`, unlike `SetManualVacancyDescriptionService`. Harmless with a single
  save, but inconsistent.
- `VacancyCoreRequest` in the contract lists `hoursPerWeek` under `required`, but its properties are
  `minHoursPerWeek` and `maxHoursPerWeek`.
