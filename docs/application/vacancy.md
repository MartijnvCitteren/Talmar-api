# Vacancy

The vacancy is the first aggregate and the start of every recruitment flow: a recruiter creates it in stages, and later
it gets published to job boards and receives candidates.

## Domain model

`Vacancy` (`domain/vacancy`) is the aggregate root, created through its builder:

| Field | Type | Notes |
|-------|------|-------|
| `id` | UUIDv7 | Generated by the builder unless given explicitly (used when loading from the database). |
| `version` | Long | Optimistic lock: `null` until the vacancy is first saved, then the version it was loaded with. See "Persistence". |
| `jobTitle` | String | Required. |
| `language` | `Language` | Required. ISO 639-1 language of the vacancy texts: `NL`, `EN`, `DE`, `FR`, upper case in the contract too, like the country code. A value outside the enum (e.g. lower-case `nl`) is a `400`. AI generation writes the draft in this language. |
| `category` | `VacancyCategory` | Required. Fixed list of 21 job categories, incl. `OTHER`. |
| `location` | `Location(country, city)` | Required; both parts non-blank. The contract restricts `country` to ISO 3166-1 alpha-2. |
| `workplaceType` | `ONSITE` / `REMOTE` / `HYBRID` | Required. |
| `hoursPerWeek` | `HoursPerWeek(minHours, maxHours)` | Required. `BigDecimal`, so part-time hours like 32.5 are exact. |
| `status` | `VacancyStatus` | `DRAFT`, `PUBLISHED`, `FILLED`, `CLOSED`. Defaults to `DRAFT`. |
| `description` | `VacancyDescription` | Optional, see below. |
| `contactPerson` | `ContactPerson(name, role, phone, email)` | Optional. Free text, not a Talmar user (often a hiring manager without an account). `role` and `phone` are optional. `email` reuses identity's `EmailAddress` (lower case). `toString` is redacted to the role. |
| `offer` | `Offer(salaryMin, salaryMax, currency, salaryPeriod, numberOfHolidays)` | Optional. Gross salary amounts (`BigDecimal`, rounded half up to 2 decimals in the constructor: `10.745` becomes `10.75`) per `SalaryPeriod` (`HOURLY`, `MONTHLY`, `ANNUAL`), a `java.util.Currency`, and full-time-equivalent holiday days (`BigDecimal`). The combination rules are contract rules, see the contract. |
| `createdAt`, `lastModifiedAt`, `lastModifiedBy` | from `BaseObject` | `createdAt` is required and passed in by the use case. |

`VacancyDescription` is a value object with five optional texts (`summary`, `jobDescription`, `tasks`, `whatWeOffer`,
`aboutUs`) and a `source`: `MANUAL` (typed by the user) or `GENERATED` (reserved; not set by any use case). A draft
from AI generation (`generation.md`) is saved through the manual endpoint and therefore has source `MANUAL`: the user
reviewed and submitted it. It is replaced as a whole, never edited field by field.

`PhoneNumber` normalises what the user typed to digits only, with a leading `+` for an international number: a
leading `00` becomes `+`, and in an international number the trunk prefix `(0)` is dropped (`+31 (0)6 12 34 56 78` and
`0031 6-12345678` both become `+31612345678`). A national number stays national, because the country code cannot be
derived. Normalising twice gives the same value. Its shape (6–15 digits, separators only) is checked against the
contract before it gets here.

The aggregate has no behaviour beyond construction and setters yet: no status transitions, no rule that
`minHours <= maxHours`. Add such rules to the aggregate when the use case that needs them is built.

## Implemented use cases

### Create a vacancy — `POST /vacancy`

`CreateVacancyService` builds a `DRAFT` vacancy from the core fields (job title, language, category, location,
workplace type, min/max hours per week), stamps `createdAt` from the `Clock`, and saves it. Returns `201` with the `VacancyResponse`.
The rest of the vacancy is added in later steps; this is the "staged creation" the contract describes.

### Set a manual description — `POST /vacancy/{id}/description`

1. `VacancyDescriptionContentValidator` rejects raw HTML/script-like tags and control characters (newline, carriage
   return and tab are allowed; rules in `TextContentRules`) → `400` naming the field. Length limits come from the contract (bean validation).
2. `SetManualVacancyDescriptionService` loads the vacancy (`404` if missing), replaces its description with a new
   `MANUAL` one and saves it (`409` if the vacancy changed in the meantime).
3. Returns `201` with the `VacancyDescriptionResponse`.

AI generation is a separate endpoint (`generation.md`) whose drafts the user edits and then submits here. This
endpoint never generates text itself, which keeps the human in control of what gets saved.

### Update a vacancy — `PATCH /vacancy/{id}`

The user changes whatever part of the vacancy they want: core fields, description, contact person or offer, in any
combination. Generation never writes to the vacancy, so an update while a description is generating does not
interfere.

1. Bean validation on `VacancyUpdateRequest`: every field is optional; the limits and whitelists of each section are
   the same as where it is first set, and the `CurrencyCode` enum allows European currencies only (another code is an
   unreadable body, `400`). The body is `application/merge-patch+json`.
2. `VacancyUpdateRequestValidator` checks the rules that combine fields → `400` naming the field:
   - `minHoursPerWeek` and `maxHoursPerWeek` come together (the missing one is named)
   - the description has no markup or control characters (`VacancyDescriptionContentValidator`, named
     `description.<field>`)
   - the offer has a salary or holidays (`offer`)
   - a salary needs `currency` and `salaryPeriod`
   - `salaryMin` is not greater than `salaryMax` (`offer.salaryMin`)
3. `VacancyUpdateRequestMapper` builds an `UpdateVacancyCommand`. A field that is left out or `null` stays `null` in
   the command. A description becomes a `MANUAL` one. The phone number is normalised (`PhoneNumber`) and the e-mail
   address lower-cased.
4. `UpdateVacancyService` loads the vacancy (`404`) and replaces every part that was sent. It leaves the rest
   unchanged, then saves (`409` on a concurrent change).
5. Returns `200` with the `VacancyResponse`. A body without fields changes nothing and returns the vacancy as it is.

Each part is replaced as a whole (`location`, `description`, `contactPerson`, `offer`), not merged field by field.
A field left out inside a part that is sent is cleared, so the cross-field rules can be checked on the request alone.
A `null` field is treated as left out, so a part cannot be cleared (see "Known gaps").

### Set the contact person and offer — `PUT /vacancy/{id}/offer` (deprecated)

The older endpoint for the creation step where the user fills in contact person and offer. It is deprecated in the
contract in favour of `PATCH`, and kept until the frontend has moved. It runs the same steps through the same
validator, mapper and `UpdateVacancyService`, with both parts required. The result is identical to a `PATCH` that
sends `contactPerson` and `offer`.

The controller logs neither request: they hold personal data.

## Contract-only operations

The contract also defines list, get, delete (soft delete, status `ARCHIVED`), publish, fill and close. None of
these is implemented: the controller answers them with `501` problem details (`EndpointNotImplementedException`). The
domain has no `ARCHIVED` status yet.

## Persistence

- Two tables: `VacancyJpaEntity` (with `language` as a `NOT NULL` column) and `VacancyDescriptionJpaEntity`, whose
  text columns have the contract's maximum lengths (1000 / 5000 / 5000 / 2500 / 2500). The description shares the
  vacancy's primary key (`@MapsId`), so a vacancy can have at most one description row. It is fetched eagerly, because
  the aggregate is always loaded whole.
- `VacancyRepositoryAdapter.save` writes vacancy and description in one cascaded save. When the description is
  removed, it deletes the row explicitly, because `orphanRemoval` does not fire when merging a freshly mapped entity
  graph.
- **Optimistic locking**: `VacancyJpaEntity.version` is a JPA `@Version` (not null, default `0`, so the schema update
  can add it to existing rows). The domain carries the version it was loaded with, because the adapter maps a fresh
  entity on every save: a `null` version tells Spring Data to insert, a loaded one makes Hibernate check it. The save
  is flushed at once, so a conflict surfaces in the adapter, which throws `VacancyModifiedConcurrentlyException`
  (`application/port/out`); `VacancyExceptionHandler` answers `409` (`ConcurrentModification` in the contract).
  It protects the time between loading and saving inside one request: two overlapping requests on the same vacancy
  cannot both win. A save must start from a loaded vacancy; saving the same unsaved domain object twice fails.
- **Contact person**: four flat columns on the vacancy table (`contact_person_name`, `_role`, `_phone`, `_email`)
  instead of an embeddable, because name, phone and e-mail are `@PersonalData` and the role is `@ProcessData`, and the
  GDPR rule classifies an embedded field as a whole. Name and role are `nvarchar` (`@Nationalized`). A row without a
  name has no contact person.
- **Offer**: `OfferJpaEmbeddable`, `offer_*` columns on the vacancy table, all `@ProcessData`. Hibernate loads it as
  `null` when every column is `null`. Salaries are `decimal(11,2)`, the currency is stored as its ISO code.
- Every other vacancy field is `@ProcessData`. The contact person's name, phone and e-mail are the vacancy's only
  personal data. `lastModifiedBy` (from `BaseJpaEntity`) is
  a user id, also process data, and it is not filled yet.

## Known gaps

- `PATCH /vacancy/{id}` treats `null` as "leave unchanged", unlike JSON Merge Patch (RFC 7396), where `null`
  removes a field. The description, contact person and offer therefore cannot be removed once set. Supporting this
  needs a way to tell an absent field from `null` in the generated model: `openApiNullable` is off, and its
  `JsonNullable` would first have to be checked against Jackson 3.
- `PATCH` allows a `jobTitle` of 0–200 characters, while `POST /vacancy` allows 2–100. Aligning them is a breaking
  contract change.
- `PUT /vacancy/{id}/offer` is deprecated. Remove it (breaking) once the frontend uses `PATCH`.
- Every part of a vacancy can be changed in every status, also `PUBLISHED`. Once publishing exists, a change to a
  published vacancy has to reach the job boards.

- The client never sends the version it last saw (no `ETag`/`If-Match`), so a user who edits a stale copy in the
  browser still overwrites a newer change. The optimistic lock only covers overlapping requests.

- `listVacancies` is declared in the contract as `GET /vacancy/{id}/generate-description` (it sits under the wrong
  path and takes a vacancy `id`). Moving it to `GET /vacancy` is a breaking contract change; do it when the listing is
  built.
- `CreateVacancyService` has no `@Transactional`, unlike `SetManualVacancyDescriptionService`. Harmless with a single
  save, but inconsistent.
- `VacancyCoreRequest` in the contract lists `hoursPerWeek` under `required`, but its properties are
  `minHoursPerWeek` and `maxHoursPerWeek`.
